✅ 审计发现复核结论：移动端横向溢出 = 测试方法假阳性（已消除，应用无需改 CSS）

结论：应用响应式正常，不存在真实移动端横向溢出缺陷，无需动 CSS。原"待修复"项撤销。
测试侧修复：L3j 移动端视口改走 CDP 真·设备模拟（依赖 websocket-client，已写入 tests/requirements.txt）；移动端溢出断言升级为硬门禁（CDP 下仍溢出才算真缺陷），无依赖时降级跳过该断言（不再误报）。重跑 L3j：移动(375) scrollW=385 == innerW=385，溢出=True，门禁通过。

二、详细发现与建议

① 安全 / 维护风险（P1）

1. extract_core.py 是危险的遗留脚本
该脚本用正则从 global-data-atlas.html 的最后一个 <script> 抽取 cMetric/regCountry 等核心函数生成 app-core.js。但当前架构已反转——核心逻辑在独立的 app-core.js，HTML 的 inline script 是纯渲染层，不含这些函数。误跑会：① 打印一堆"未找到函数"；② 用残缺内容覆盖 app-core.js（清空全部核心函数）；③ 重写 HTML（移除未匹配的片段，可能破坏结构）。
建议：直接删除 extract_core.py，或在文件首加硬 guard——检测 window.COUNTRIES 是否已在 app-core.js 时立即 sys.exit(1) 并提示"core 已独立，勿再抽取"。README 也明确警告过，但脚本本身仍在仓库，风险点未消除。
2. echarts 实例未 dispose → 内存泄漏
renderTrendChart(L522) 与 renderTrendCompare(L556) 每次都 const tc=echarts.init(el) 创建新实例。每次面板切维度/年份/区域时，foldTrend/renderTrendCompare 用 innerHTML 重写容器 DOM，旧 echarts 实例失去 DOM 引用但实例对象、事件监听、动画计时器仍驻留。window.__trendChart 只持最新一个，旧的全丢失引用却未被 dispose()。用户高频点击国家/省份时泄漏累积。
建议：渲染前先 if(window.__trendChart) window.__trendChart.dispose();；或改为"单实例复用 + setOption"模式（维护一个模块级 chart 实例，仅 setOption 更新）。趋势图容器固定一个 DOM 即可。
3. "最近可得年份"回退逻辑散落 8+ 处且策略不一致
同一语义（在数据缺失年份时取最近可得年，偏好前/后可配）在 cMetric、cGrowth、usGdpUsdM、usGdpYear、cnGdpRMB、cnGdpYear、regCountry.ext、regCountry.extYear、regCountry.growth、cmpGetData 重复实现。实现方式不统一：有的用 .filter().sort().pop()/[0] 组合（L365），有的用 for 最小距离循环（L262-264），回退偏好（前/后）也不完全一致。可读性与正确性风险高——某处改了回退策略，另一处不会同步。
建议：抽一个工具函数 nearestYear(availYears, target, preferBefore=true)，所有取数统一调用；regCountry.get 内部也走它，消除散落的 Object.keys(o.years).map(Number) 重复。

② 构建 / 部署（P2）

4. build.sh 缓存指纹 ?v 重复运行不刷新
L37-39 用 sed "s|src=\"vendor/app-core.js\"|...?v=HASH|" 注入指纹。首次 build：source 是 src="vendor/app-core.js" → 注入 ?v=H1。改 app-core.js 后二次 build：cp -R 已把 dist/app-core.js 更新为 H2 内容；md5 校验通过（source==dist 内容）；但 sed 在 dist HTML 找的是 src="vendor/app-core.js"——此时 dist HTML 已是 ?v=H1，匹配不到 → ?v 不更新。结果：dist HTML 引用 ?v=H1，文件却是 H2 内容 → URL 不变 → 浏览器/CDN 按旧 URL 缓存，用户可能拿到旧 JS（最近的修复 commit "fix cache" 正是为此，但 sed 没覆盖二次运行场景）。
建议：sed 同时匹配已存在的 ?v=...，如 s|src="vendor/app-core.js\(?v=[a-f0-9]*\)\?"|src="vendor/app-core.js?v=${H}"|；或注入前先 normalize（去掉 ?v）再注入。
5. dist 携带非运行时文件（体积冗余）
cp -R vendor/. dist/vendor/(L17) 把整个 vendor 目录带入 dist，包括 world.json(1MB，构建源，运行时只加载 world.js)、_enmap.json、各 .bak。已验证 world.json / _enmap.json 被 build_countries_multi.js 等构建脚本引用——是构建源输入，源码应保留；但 dist 运行时并不需要它们，纯属部署体积浪费。
建议：build.sh 同步 dist 时排除非运行时文件（world.json、_enmap.json、*.bak、__pycache__），或直接 rsync --exclude。可减 dist 约 1MB+。

③ 代码质量 / 可维护性（P2）

6. US_STATES_GDP 运行期 mutate 单位（反模式）
app-core.js L138-191 定义 US_STATES_GDP[k].gdp 单位"万亿"（注释 L338）。但 HTML L343-356 在运行期把它乘 RATE23*1e12 就地改成 CNY 元（并在 window.US_TS 存在时覆盖）。这是"常量定义时一个单位、运行时再 mutate 成另一个单位"的反模式，依赖"inline 段在 app-core 之后执行"的隐式顺序，且 US_STATES_GDP.gdp(万亿) 与 US_TS(USD 百万序列) 双份存储易漂移。
建议：数据层统一——US_STATES_GDP 只存权威值（USD 百万 + 年份），regUSState.get 统一经 gdpApply 折算，删除运行期 mutate 逻辑。
7 & 8. loadXxx / showXxxPanel 高度同构，重复度高
四个 loadChina/US/Japan/NUTS 都是"懒加载边界 → registerMap → features.map 取数 → setOption → 面包屑 → renderOverviewMetrics → 排行"；六个 showXxxPanel 都是"构造 GDP/人口/面积 三卡 → metricCards → renderDashboard"。新增区域（如韩国、印度省级）需同时改 2 处，易漏。
建议：抽 renderGeoLayer({mapName, geoGetter, normalize, drillable}) 与 buildRegionPanel({name,en,level, resolvers:{gdp,pop,area}, growth}) 两个模板，把差异参数化。LAYERS/DRILLABLE 注册表已搭好骨架，顺手即可收敛。
9. 数据脚本安全性（eval / 非原子写 / 覆盖风险）
fetch_ext_data.py L37 用 eval(m.group(1).replace('null','None')) 解析 JS 对象（不良实践，虽本地可控）；L88-92 直接 open('vendor/ext_indicators.js','w') 覆盖，无自动备份、非原子写，且该脚本是全量重拉——会丢失文件里的任何 manual 修正。仅 stdout 打印"建议先备份"，依赖人记住。fetch_ext_merge.py 虽读旧数据 merge，但同样非原子写。
建议：① 用稳健解析替代 eval（正则提取 + json.loads，或 js2py 受限）；② 写临时文件再 os.replace() 原子替换；③ 写入前自动 cp 时间戳备份到 /tmp；④ 失败回滚到备份。降低"一键跑坏数据"风险。
